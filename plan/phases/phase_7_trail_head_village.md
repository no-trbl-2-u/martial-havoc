## What the book gives, and what the spec fills in

`docs/rules/cities.md` (MH p.46-51) describes a *city*: seven
locations, of which three are mechanical (R57 Gambling House, R58
Temple, R63 Chaguan), plus the City Services price list (R64) and the
City-encounters table (R65). `docs/world/market.md` (MH p.52-55) is a
separate table of goods.

The adventure has no settlement at all: `docs/campaigns/the-5-treasures/`
starts at the Flat-top mountain and the Lotus Flower cave
(`map.md` adjacency: Flat-top mountain -> Cave entrance). So the
village is `spec.md`'s Horizon, not the book's — "a trail-head village
is a City on fixed data". It ships as **fixed data**, not a roll: the
same three locations every run, so the cave has a doorstep that does
not change under the player.

That makes the split of labels sharp, and it must be honoured:

- The **procedures** are the book's. Buying at printed prices is R64/the
  Market table; the Temple's Spirituality check for +1 LUCK is R58; a
  night's rest is R40 plus `spec.md`'s sealed +4 ENDURANCE, already in
  `packages/engine/src/healing/healing.ts`.
- The **village** — that there is one, that it has these three
  locations, that a trail leaves it for the mountain — is `invention`,
  cite `spec.md, Horizon`.
- One-Temple-check-per-day is `reading` I-58.

Nothing in this phase reopens a sealed rule. `spec.md` and the two PDFs
are not touched.

## The three locations (locked)

here so no later tick re-litigates them; they are exactly the three the

| Location | Procedure | Reads | Label |
|---|---|---|---|

named entry point.

## Content — `packages/content/data/world/village.json`

`kind: "list"`, `label: "invention"`, `cite: "spec.md, Horizon"`,
`docs: "docs/rules/cities.md"`. One record per location plus the trail:

```
{ id, cite, kind: "location" | "trail",
  name, blurb, procedure: "buy" | "temple" | "inn" | null,
  destination: string | null }
```

Every `blurb` is authored copy and therefore lives here, never in a
component (rule 7). The village's own name is authored: **Fen Pass**
(invention; a pass at the foot of the mountain). Exported from
`packages/content/src/world/index.ts` as `villagePlaces`,
`villagePlaceById`, `villageLocations` and `villageTrail`, in the same
shape every other table there uses. `schema/content.schema.json` gains
the record kind; the content package's schema test is the validation
leg (agents.md rule 3 — there is no separate `data:validate`).

## Engine — `packages/engine/src/village/`

Small files in a folder (hard rule 7), no React, no dice of its own
(rule 7 of `agents.md`): the `DiceSource` is injected exactly as
`checks.ts` and `region.ts` take it.

| File | Exports |
|---|---|
| `money.ts` | `SP_PER_GP = 10`, `toSilver`, `fromSilver`, `priceInSilver(record)`, `spend(purse, cost)` |
| `market.ts` | `buy(input)` — one purchase against a purse |
| `temple.ts` | `templeVisit(input)(dice)` — the Spirituality check |
| `inn.ts` | `stayTheNight(input)` — meal + `nightsRest` |
| `village.ts` | re-export barrel + `arriveAtVillage`/`day` helpers |
| `behaviours.ts` | the `{label, cite}` rows for every export above |
| `village.test.ts` | colocated |

Locked decisions inside these:

1. **Money is silver.** `Master.gold` is GP (R03); the Market prints
   both `priceGp` and `priceSp`. Converting once to SP (1 GP = 10 SP,
   MH p.52) is the only way to compare them without floats. `buy`
   returns a purse in SP and the GP/SP pair for display.
2. **`buy` never mutates and never refuses silently.** Too little
   money returns `{ bought: false, reason: 'insufficient' }` with the
   purse unchanged. An unknown item id is the same shape with
   `reason: 'unknown-item'` — total functions, no throws (matches
   `lookup.ts`'s total-lookup contract).
3. **Incense is required at the Temple** (R58: "If you have incense").
   `templeVisit` takes `hasIncense: boolean`; false returns
   `{ attempted: false }` without rolling. The engine does not model an
   inventory — the caller says whether the Master has it.
4. **One Temple check per day** (I-58). `templeVisit` takes
   `visitedToday: boolean`; true returns `{ attempted: false, reason:
   'already-visited-today' }`. The reading's "a second risks -1 LUCK"
   is **not** applied: the reading says *risks*, and inventing the
   trigger would be a rule the book declines to give. Recorded as a
   Follow-up.
5. **The inn charges before it heals.** `stayTheNight` runs `spend`
   first; an unaffordable stay returns the state untouched. The room
   price is a village record field, not a hardcoded number.
6. **A meal is ENDURANCE's partial +4** (the healing table's "a meal"
   row), and the night is `nightsRest`. They are the *same* +4, applied
   once, not twice — `healing.ts` caps at `initial`, so a Master at full
   ENDURANCE gains nothing and `restored` is 0. `stayTheNight` returns
   both `Heal` records so a UI can say which did what.
7. **No City-encounters roll in the inn.** R65 is a city procedure the
   row does not name; the village is fixed data and an encounter roll
   is not fixed. Follow-up.

## Labels

Every export above gets a row in `village/behaviours.ts` and is
registered where `labels:check` looks (same wiring as
`region/behaviours.ts` -> `packages/engine/src/index.ts`). Expected
labels: `village.is-fixed-data`, `village.trail-leads-to-the-cave`
(both `invention`, `spec.md, Horizon`); `village.buy-at-printed-price`
(`rule`, MH p.52-55); `village.gold-is-ten-silver` (`rule`, MH p.52);
`village.temple-recovers-one-luck` (`rule`, MH p.47 R58);
`village.temple-needs-incense` (`rule`, MH p.47 R58);
`village.one-temple-check-per-day` (`reading`, I-58);
`village.inn-charges-before-it-heals` (`invention`, `spec.md, Horizon`);
`village.nights-rest-is-the-sealed-four` (`rule`, MH p.31 R40;
`spec.md`).

`labels:check` also enforces the rules panel: **every behaviour needs
exactly one note** in `packages/content/data/app/behaviour-notes.json`,
keyed `ref` -> behaviour id, and a `reading` note must additionally
answer all four panel questions (`says`, `silent`, `source`,
`reversed`). So `village.one-temple-check-per-day` — the one reading
here — ships with all four fields, and every other new behaviour ships
with a `text`. A behaviour without a note is a red gate, not a warning.

## Tests

Colocated, alongside the code (hard rule 6):

| Test | Asserts |
|---|---|
| content schema | `village.json` validates; three `kind: "location"` + one `kind: "trail"`; every record has a `cite` |
| `money` | 1 GP = 10 SP round-trips; a GP-priced and an SP-priced item compare correctly |
| `buy` | affordable purchase debits exactly the price; unaffordable leaves the purse untouched with `reason: 'insufficient'`; unknown id returns `'unknown-item'` |
| `templeVisit` | success recovers exactly 1 LUCK; failure recovers 0; no incense does not roll; a second visit the same day does not roll; a double six fails (sealed) |
| `inn` | an affordable stay debits the room and returns both heals; ENDURANCE at `initial` gains 0; unaffordable stay changes nothing |
| labels | every village export has a `{label, cite}` row **and exactly one rules-panel note** (this is `labels:check`, not a new test) |

Dice come from the fixed/scripted `DiceSource` the other engine tests
already use — no randomness in a test.

**E2E:** none new. Phase 8 owns the screens; adding an e2e for a
surface that does not render yet would be a green test proving
nothing.
