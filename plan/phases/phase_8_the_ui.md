## This is v1

The build plan marks this row `(v1)` and means it. Phase 8 ships the
**first** interface that works end to end on the real engine — not the
settled design of the product.

The layout was picked on 2026-09-06 from three candidates, rendered on
a prototype beat, before anyone had played the cave to its ending.
That is the best evidence available *now*, and it is thin evidence.
Phase 10 — the cave played through in the app with the PDF closed — is
the first time anyone learns what this UI is like to use for an hour,
and findings from that sitting are an expected outcome of the plan, not
a defect report against this phase.

So: `/iterate` may polish v1 freely. Re-opening the layout, the
navigation model or the screen set is a plan-level change and needs its
own phase, through `/expand` or `/oversight`. And the thing that makes
a v2 cheap is the standing split — no rule, no table, no citation lives
in a component (rule 7) — which this phase must not erode under
deadline.

## Outcome

The web export stops being a prototype of three screens and becomes the
game: a Master is created in the book's order, the cave is walked, a
fight is won, the village is visited, and the campaign record is
exported and read back — all at phone width, all on the engine and
content already shipped.

**Done when** (the build-plan row): a Playwright run creates a Master
and wins a fight on the web export; the layout decision is recorded.

## The three candidates (8a)

All three render the *same* beat from the *same* state: the authored
line, the last result with both dice and its label pill, the menu the
rules allow, the free-text passage field, the roll bar with manual
entry and the override count. They differ in **arrangement**, which is
the only thing an operator can usefully pick between; the woodblock
tokens (`apps/app/src/theme/tokens.ts`) are the same in all three,
because the palette is already decided in `design/INDEX.md` and
re-opening it would be a different question.

| | Layout | The bet it makes | Costs |
|---|---|---|---|
| **A** | **Scroll** — the shipped prototype. Line, result, scrolling menu, roll bar at the foot. | The authored line is the point; the player reads before they act. | The menu can fall below the fold on a long line; the primary action is a thumb-stretch from the top of the page. |
| **B** | **Sheet** — the line scrolls alone in the upper page; the menu is a fixed bottom sheet of full-width rows above the roll bar; the result overlays the top of the sheet. | Everything actionable lives in the bottom third, where the thumb is. Nothing the player can press ever scrolls away. | The line gets less room; the result covers part of the menu when it lands. |
| **C** | **Ledger** — the line, the result slip, then the deeds already done here as a running transcript beneath it. The menu is a compact two-column grid above the roll bar. | The screen *is* the campaign record, growing. A player can see the last four deeds without leaving the beat. | Denser; the transcript competes with the result slip for the middle of the page; two-column menu rows drop each option's note and truncate longer titles. |

Each is a component in `apps/app/src/layouts/`, composing the shared
pieces extracted to `apps/app/src/components/beat/`. Extracting first
is the point: whichever layout wins, the pieces are already the ones
the rest of the phase builds on, and the two losers delete cleanly.

## Decisions made upfront — DO NOT ASK

1. **Tokens are not re-opened.** `design/INDEX.md` decided the
   woodblock palette and the three type families. The candidates differ
   in arrangement only, so the operator is asked one question, not two.
2. **The layout flag is temporary.** `?layout=` exists for 8a and is
   **deleted** in 8b along with the two losing components. A shipped
   product does not carry an unchosen design behind a query string.
3. **No router.** The app is one page with a screen enum in state, as
   the prototype already is, and the e2e already asserts the
   single-page fallback. Adding a router to a phone-first offline app
   would be a dependency with no user in it.
4. **Creation never refuses.** R02-R19 pools are reported and flagged,
   never blocked — `spec.md` is explicit, and Yin's printed overspend
   is the proof case.
5. **The free-text field is always present**, on every beat, whether or
   not the beat asks for one (spec.md).
6. **Every rolling surface offers manual entry**, and every manual
   entry increments the override count. A player with real dice on the
   table is the assumed player.
7. **Screenshots are not a verify leg.** `npm run screenshots` writes
   PNGs for the operator; fonts differ per machine and a pixel diff
   would be a flaky gate. The e2e asserts structure, never pixels.
8. **Mobile is the target, not a reflow.** 390x844 is the reference
   (`design/V1-DESIGN-PROMPT.md`); wider viewports centre the same
   frame rather than re-laying it out.
